# 权限

[English](permission.md) | 中文

MaoTa 在用户自己的机器上执行命令、改文件，所以有一个决定必须由人来做：这个操作到底跑不跑。本文档负责这道闸门：它落在哪、答什么、记什么，以及刻意不做什么。闸门是一个插件，不是内核功能；内核像路由其它能力一样路由 `permission`，从不看命令。

<a id="闸门落在哪"></a>
## 闸门落在哪

每一次工具调用都走同一个漏斗：`agent-core` 调 `tools` 能力，分发器查出工具，把参数转给 `tool.<name>/run`。闸门也属于这里，因为这是调用碰到机器之前最后一个能拦住它的地方。

这一版把闸门放在漏斗往里一步：判断某个操作是否需要征得同意、并去征得同意的，是工具自己，不是分发器。发起询问的只有 `tool-pwsh` 一个，它停在三种形状上（`rm `、`> /etc/`、`chmod 777`）。这里不交付规则表，因为"什么算破坏性"是执行它的那个工具自己的性质：第二个想要闸门的工具发同样的 `permission/request` 调用，不需要改动这里。

`tools.call` 仍然是"把闸门放在中央"时的扩展点，这一版不实现那条转发。无论闸门放在哪一层，内核都一无所知：不认识工具、不认识命令、不认识权限。

<a id="三档策略"></a>
## 三档策略

策略按会话、按工作目录分别生效，于是同一个项目可以无人值守，另一个项目等人回答。

| 档位 | 命中风险的操作用 | 记下什么 |
|---|---|---|
| `ask` | 发布一个问题，调用在那里等回答。 | 这个提问，以及它得到的回答。 |
| `auto` | 不问，直接放行。 | 一条决定，归因写 `policy:auto`。 |
| `full` | 工具连自己的命令行都不判断，也从不询问。 | 不记：这个操作根本不是一个提问。 |

`ask` 是默认档，也是唯一能拦住调用的档。策略变更本身也留痕，所以某个会话什么时候被切成 `full`、被谁切的，都查得到。

工具在每次调用前读一次策略，所以换档在下一个命令上生效，而不是等下次启动。策略跟着会话存，页面刷新或部署重启之后依然成立。

<a id="契约"></a>
## 契约

插件提供 `permission`，版本 `1.0.0`，读三个配置键：`mode`（从未选过档的会话的回退值，默认 `ask`）、`dir`（默认 `$MAOTA_HOME/permissions`）、`max_records`（默认 `500`）。

| 方法 | 参数 | 回答 |
|---|---|---|
| `policy` | `session_id`、`cwd` | `{ mode }`：会话自己的选择，或配置的回退值。没有文件的会话拿到回退值，不报错。 |
| `set_policy` | `session_id`、`cwd`、`mode` | `{ mode }`。不属于三档的 mode 报 `-32602`。把会话设成它已有的那一档不产生任何变化，也不追加记录。 |
| `request` | `session_id`、`cwd`、`tool`、可选 `call_id`、可选 `reason` | `{ outcome }`，见下面的词表。 |
| `answer` | `id`、`decision`（`allow` 或 `deny`） | `{ settled: true }`。迟到或未知的 id 报 `-32602`，这条回答被丢弃。 |
| `pending` | 可选 `session_id` | `{ requests }`：所有还在等的问题，刷新过的页面据此重建卡片。 |
| `register_answerer` / `unregister_answerer` | 无 | `{ answerers }`。每个插件一条，用它的 caller 标签做键，所以重启的前端替换的是自己那条注册。 |

`request` 的回答是封闭的四种之一，只有第一种是放行：

| 结果 | 含义 |
|---|---|
| `allowed-once` | 就这一次可以跑。什么都不记：下一个命中的操作还会再问。 |
| `rejected` | 人说了不行，或策略说了不行。 |
| `cancelled` | 还没等到决定问题就被撤回，或调用被取消。 |
| `unavailable` | 没人能答：没有注册的应答者，或问题根本问不出去。 |

只有 `ask` 且至少有一个注册应答者时才发布问题。`auto` 与 `full` 立刻答 `allowed-once`，`decided_by` 分别写 `policy:auto` 与 `policy:full`，且什么都不发布。凡不是 `allowed-once` 的都是拒绝，而拒绝就是调用方必须照着办的结果：能力缺席、调用抛错、回答的词不在四个字里，一律归到 `unavailable`，所以没有任何一条失败路径能变成默认同意。

发布两个事件，尽力而为：`permission.requested { id, session_id, tool, call_id?, reason?, subagent?, at }` 与 `permission.settled { id, outcome, decided_by, at, subagent? }`。它们只是给正好在听的前端的通知。持久文件加 `pending` 才是真相；丢一条事件顶多重画一次，绝不会丢一个决定。

请求刻意不携带工具参数。前端靠 `call_id` 把问题和它所属的那次工具调用对上，这个值由 `agent-core` 按模型请求的那次调用的 id 作为 host 参数注入。

有一个可选字段确实会跟着来：`subagent`，即发起这次调用的子代理的 `{ id, type, description }`；会话自己发起的调用没有它。子代理的调用是以父的 `session_id` 和父那次 `task` 调用作为 `call_id` 到达闸门的，所以这个标签是唯一说明问题出自某个子代理、以及是哪一个的东西。它落进发布的事件、`pending`，以及两条审计记录，于是卡片能出现在派出这个子代理的那一行下面，重启之后也还能从文件里重建。

<a id="审计文件"></a>
## 审计文件

每个会话、每个工作目录一个文件：`$MAOTA_HOME/permissions/<cwd>/<session_id>.json`，其中目录对工作目录的编码与会话存储一致，空工作目录落成 `default`。

```json
{
  "schema_version": 1,
  "session_id": "…",
  "cwd": "E:\\work",
  "mode": "ask",
  "records": [
    { "kind": "asked", "at": "…", "id": "…", "tool": "pwsh", "call_id": "…", "reason": "…", "subagent": { "id": "sub-3f2a", "type": "explore" } },
    { "kind": "decided", "at": "…", "id": "…", "outcome": "allowed-once", "decided_by": "web", "subagent": { "id": "sub-3f2a", "type": "explore" } }
  ]
}
```

文件守一条不变式：每条 `asked` 恰好配一条同 `id` 的 `decided`。没有 `asked` 的 `decided` 只在"策略自己做的决定"这一种情况下合法，这也是它的 `decided_by` 必须以 `policy:` 开头的原因。截到 `max_records` 时保留最新的记录，且绝不把一次提问和它的决定拆开；开头那条丢了问题的记录跟着一起丢。

写入沿用会话存储的做法：整个文件先序列化到临时名再改名覆盖，读的人不会看到半条记录。策略变更也是一条记录，`kind: "policy"`。

<a id="卡片与线路"></a>
## 卡片与线路

这一版交付的应答者只有 web 插件。它在启动时注册自己、订阅那两个主题，把它们转成 `permission.request` 与 `permission.settled` 推给页面，并在页面原有的方法之上多提供四个 RPC：`permission.get`、`permission.set`、`permission.answer` 与 `permission.pending`。页面为每个在等的问题渲染一张卡片，按 `call_id` 对上那条已经在流式输出的工具调用，并在刷新或重连之后用 `permission.pending` 重建卡片。子代理问的问题用同一套对法，于是卡片落在父那行 `task` 下面，并写明是哪个子代理在问。

卡片只给两个回答，且不记事：允许这一次，或拒绝。没有"总是允许"，因为记住的授权就是规则，而规则正是这一版不交付的东西。

档位选择器也不是页面本地的设置：它从插件读这个会话的档，再写回插件。没有活动会话、以及一轮正在跑的时候它都是禁用的，这样档位不会在一次已经读过它的调用底下被换掉。

CLI 不注册应答者。终端驱动的 `ask` 部署因此会拒绝命中风险的操作，并把理由写回工具结果，这是既定的 fail-closed 语义，不是缺陷：问不出口的前端就不该放行。

<a id="本文不覆盖的部分"></a>
## 本文不覆盖的部分

- 闸门只决定一个操作跑不跑，一旦跑起来它能碰什么，本文不管：文件工具保留自己那套工作区约束，而 shell 命令仍然只被 shell 提供方限制。
- 没有分类器判断什么算破坏性。唯一的发起方只读三种固定形状，藏在这三种形状之外的破坏性命令不会被点名。
- 没有规则表、没有硬拒绝列表、没有记住的授权：每一次命中的操作都是一个新问题。
- 没有多应答者仲裁。任何已注册的应答者都能结束一个问题，先到的回答生效。
- 没有沙箱。被允许的命令按它一贯的方式运行。
